# 一、进程 / 线程 / 协程

## 1.0 进程和线程的区别

| **维度** | **进程 (Process)** | **线程 (Thread)** |
| --- | --- | --- |
| **定义** | 运行中的程序实例，拥有独立的内存空间。 | 进程内部的一个执行单元，共享进程资源。 |
| **资源拥有** | 拥有独立的地址空间、文件句柄、全局变量等。 | 共享所属进程的资源，但拥有自己的栈和寄存器。 |
| **开销** | 创建和销毁开销大，切换速度慢（涉及内核态切换）。 | 创建和销毁开销小，切换速度快（在同一进程内）。 |
| **并发性** | 不同进程间互不影响。一个进程崩溃，不影响其他。 | 同一进程下的多个线程高度协作，但也易互相影响。一个线程崩溃，容易导致整个进程崩溃 |
| **健壮性** | 一个进程崩溃通常不会影响其他进程（隔离性好）。 | 一个线程崩溃（如段错误）可能导致整个进程崩溃。 |

面试官通常考察**资源分配**与**调度执行**的理解

- **本质区别**：进程是**操作系统分配资源**的最小单位（如内存、文件描述符）；线程是**程序执行/CPU调度**的最小单位。
- **内存空间**：
    - **进程**：拥有独立的虚拟内存地址空间（Code, Data, Heap, Stack）。
    - **线程**：共享所属进程的堆 (Heap) 和全局变量，但拥有**私有的栈 (Stack)** 和寄存器/程序计数器 (PC)。
- **健壮性**：进程间相互隔离，一个进程崩溃不影响其他；一个线程崩溃（如空指针、栈溢出）通常会导致整个进程直接 `Segmentation Fault`。
- **切换开销**：进程切换涉及虚拟地址空间的切换（TLB 刷新）、硬件上下文切换，开销大；线程切换只需保存少量寄存器状态，开销极小。
- 默认线程栈空间通常是 8MB（Linux）

## 1.1协程和线程的区别

1. **核心区别**
    - **线程**是内核调度的最小单位，抢占式执行（内核可强制切换线程）；**协程**是用户态调度，协作式执行（必须主动`yield/await`才能切换，无抢占）。
    - 线程有内核栈 + 用户栈，切换涉及内核态/用户态切换；协程只在用户态切换，不进入内核。
2. **为什么更轻量**
    - 协程**不占用额外内核资源**，栈空间很小（通常几 KB ~几MB），可以轻松开启上万甚至几十万协程。
    - 切换只需要保存和恢复**少量上下文（寄存器、协程栈、程序计数器）**，完全在用户态完成，不需要陷入内核。

## 1.2为什么客户端是线程、服务器是协程

客户端线程的优点：

- UI 必须运行在主线程，把一些其他的读写，修改等操作放在子线程，利用多核的性质避免卡顿。
- 线程资源隔离（如后台线程崩溃不影响 UI 主线程），协程共享线程资源（一个协程崩溃会导致线程内所有协程挂掉），客户端无法接受这种风险。
- 协程是在一个线程上运行的，本质上同时只能执行一个操作，如果客户端主线程偶尔执行计算操作，会导致显示效果卡顿。

服务器协程的优点：

- 后端高并发场景的痛点是提升 IO 利用率，协程在 IO 等待时主动挂起，IO 就绪时恢复，CPU的利用率更高；而线程在IO等待时会被挂起，大量线程空等，导致CPU浪费。
- 高并发情况下，协程占用的空间更少（1-4KB），10w协程仅400MB内存，并且协程不占用内核资源，单服务器可以轻松支持高并发。

## 1.3线程上下文切换的开销

开销类型：

- 寄存器保存 / 恢复
- 切换栈指针到目标线程的栈基址。
- TLB 块表的刷新
- 内核调度的开销。
- 不同进程的线程之间切换还涉及到页表的切换

## 1.4 为什么上下文切换代价大

**核心细节**：

- **TLB失效**：**CPU私有，切换进程的时候CPU 会清空整个 TLB**。新进程刚开始运行时，所有的内存访问都会发生 **TLB Miss**，必须去查内存中的多级页表。线程切换因为共享地址空间，TLB 往往能保留。
- **Cache Pollution（缓存污染）**：切换到新进程后，CPU L1/L2 缓存里的数据对新进程毫无用处，必须重新从内存加载，产生大量 Cache Miss。

## 1.5 写时复制

### 2.1 概念

**核心思想**：如果有多个调用者同时请求相同的资源，它们会共同获取相同的指针指向同一份资源，直到某个调用者试图修改资源内容时，系统才会真正复制一份副本。

### 2.2 原理

1. **共享页面**：调用 `fork()` 时，内核并不复制物理内存，而是让子进程的虚拟地址空间指向与父进程相同的物理页。
2. **只读标记**：内核会将这些共享的物理页权限设置为 **Read-Only**。
3. **触发异常**：当父进程或子进程尝试写入这些页面时，CPU 硬件会触发一个 **缺页异常 (Page Fault)**。
4. **按需复制**：内核捕获异常后，发现是写操作且页面被标记为 COW，这时才分配新的物理页，将原数据拷贝过去，并更新页表指向新物理页，最后赋予读写权限。

### 2.3 性能问题

1. **性能波动**：写操作时会有突发的开销（分配内存 + 数据拷贝）。对于实时性要求极高的系统，这种不确定性需要关注。
2. **内存碎片**：频繁的 COW 触发可能导致大量零散的物理页分配。
3. **实现复杂性**：需要内核（页表、异常处理机制）与硬件的紧密配合。

## 1.6 线程数量和CPU的关系

对于计算密集型：线程数 ≈ CPU 核数。因为：

- 每个任务都在“占满CPU”
- 多开线程只会导致**上下文切换 + 抢CPU**

对于IO密集型：线程/协程数 >> CPU核数。
线程数 ≈ CPU核数 × (1 + 等待时间 / 计算时间) 因为：

- 大部分时间在“等待”
- CPU是空闲的

# 二、锁

## 2.1 mutex / 自旋锁 / 读写锁

| 锁类型 | 底层原理 | 核心开销 | 适用场景 | 字节工程实践 |
| --- | --- | --- | --- | --- |
| std::mutex（互斥锁） | 阻塞时放弃CPU，线程进入内核态等待，解锁时唤醒 | 内核态 / 用户态切换（3~10μs） | 临界区耗时中等 / 较长
IO 操作、函数调用、循环计算
 | 绝大多数业务场景（如接口限流、资源保护） |
| 自旋锁（无标准库实现） | 不放弃 CPU，循环 CAS 尝试加锁，直到成功 | CPU 空转开销（无内核切换） | 临界区耗时**极短**（<1μs）、竞争频率极低 | 底层组件（如内存池链表修改、协程调度器）

 |
| std::shared_mutex | 读共享、写排他：读锁可多线程持有，写锁独占；写优先级通常高于读（C++17） | 读锁开销≈自旋锁，写锁≈mutex | 读多写少（读占比 > 90%）、临界区耗时中等 | 缓存系统、配置中心、日志模块 |

自旋锁的简单实现

```jsx
atomic<bool> flag=false;

void lock(){
	while(flag.exchange(true,std::memory_order_acquire)){}
}

void unlock(){
	flag.store(false,std::memory_order_release);
}
```

## 2.2 递归锁

1. **适用场景**（仅 2 种合法场景）：

递归锁允许**同一线程多次加锁**（解锁次数需与加锁次数一致），仅适用于：

- 场景 1：递归函数中访问临界区（如递归遍历树结构时修改节点）；

```jsx
std::recursive_mutex rmtx;
void traverse(Node* node) {
    if (!node) return;
    std::lock_guard<std::recursive_mutex> lock(rmtx);
    node->count++; // 临界区
    traverse(node->left); // 同一线程再次加锁，递归锁允许
    traverse(node->right);
}
```

- 场景 2：类的成员函数互相调用，且都需要加锁（如`A()`调用`B()`，两者都需锁保护）；

1. **问题**
- **性能开销更高**：递归锁需要存储「加锁次数」和「所属线程 ID」，每次加锁 / 解锁都要校验，开销比`std::mutex`高约 20%；
- **死锁风险仍存在**：若多个递归锁交叉使用（如线程 1 持有锁 A 请求锁 B，线程 2 持有锁 B 请求锁 A），仍会死锁；

## 2.3 死锁

1. 死锁的四个必要条件 & 破坏方法

| 必要条件 | 定义 | 如何破坏（字节工程实践） | 代码示例 / 落地手段 |
| --- | --- | --- | --- |
| 1. 互斥条件 | 资源（锁）只能被一个线程持有，不能共享 | 无法破坏（锁的核心就是互斥） | 无（只能通过其他条件规避） |
| 2. 持有并等待条件 | 线程持有已获取的锁，同时等待其他线程持有的锁 | 一次性申请所有锁 / 申请不到则释放已持有的锁 | ① 锁排序（所有线程按同一顺序加锁）；② `std::lock`批量加锁 |
| 3. 不可剥夺条件 | 线程持有的锁不能被其他线程强制剥夺，只能主动释放 | 申请新锁失败时，释放已持有的锁 | ① 用`std::unique_lock`的`try_lock`+ 超时；② 自旋锁加超时重试 |
| 4. 循环等待条件 | 线程 A 等线程 B 的锁，线程 B 等线程 C 的锁，线程 C 等线程 A 的锁，形成循环等待 | 打破循环：所有线程按固定顺序加锁 | 锁排序（如按锁的地址 / ID 从小到大加锁） |

比如不可剥夺条件：

```jsx
#include <chrono>
#include <thread>

bool safe_lock(std::unique_lock<std::mutex>& lk1, std::unique_lock<std::mutex>& lk2) {
    // 尝试加锁，超时时间10ms
    if (lk1.try_lock_for(std::chrono::milliseconds(10))) {
        if (lk2.try_lock_for(std::chrono::milliseconds(10))) {
            return true;
        }
        lk1.unlock(); // 申请不到lk2，释放已持有的lk1 → 破坏不可剥夺
    }
    return false;
}
```
