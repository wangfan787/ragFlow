  ### 当前正式 chunker 的隐藏问题

  虽然 backend/src/chunking/chunk_config.py 把 parent_max_tokens 和 child_max_tokens 描述成“硬上限”，但 backend/src/chunking/block_merge.py 中存在破坏该承诺的分支：

  - 单个 block 超过 Parent 上限时，会把完整 block 单独作为 Parent。
  - 无标点长段落无法按句子切开时，会整体作为 Child。
  - code/table 配置为整体保留时，也可能超过上限。

  因此当前正式项目也还没有做到真正的“任意输入都不超过 chunk 硬上限”。

  RAGFlow 的 _split_oversized_unit() 更完整：

  1. 先尝试按空白拆分。
  2. 空白拆分后按 token 预算贪心合并。
  3. 单个连续字符串仍然超限时，用二分查找字符边界。
  4. 保证每个输出块确实不超过 token 预算。

  这部分属于核心算法，应当参考，不是企业级冗余。

  ## 三、切块策略的核心取舍

  ### 方案 A：RAGFlow 式单层 chunk

  Document
    ├── Chunk 0（约 512 token）
    ├── Chunk 1（约 512 token）
    └── Chunk 2（约 512 token）

   优点                               缺点
  ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━  ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
   数据模型简单                       返回上下文可能不够完整
  ─────────────────────────────────  ──────────────────────────────────
   每段文本只保存和 embedding 一次    需要 overlap 或邻接 chunk 扩展
  ─────────────────────────────────  ──────────────────────────────────
   评测和 chunk→doc 聚合容易解释      小 chunk 与大 chunk 取舍需要调参
  ─────────────────────────────────  ──────────────────────────────────
   更接近 RAGFlow 默认主链路          不具备天然 small-to-big

  适合作为 T2Retrieval dense retrieval baseline。

  ### 方案 B：当前项目的父子分块

  Parent 0（约 512 token）
    ├── Child 0（约 128 token）
    ├── Child 1（约 128 token）
    └── Child 2（约 128 token）

   优点                                     缺点
  ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━  ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
   Child 精准召回，Parent 提供完整上下文    当前同时索引 Parent 和 Child，产生重复候选
  ───────────────────────────────────────  ────────────────────────────────────────────
   不需要传统 overlap                       向量数量和 embedding 成本更高
  ───────────────────────────────────────  ────────────────────────────────────────────
   面试中有较强的系统设计表达力             需要 family 去重和 parent 回查
  ───────────────────────────────────────  ────────────────────────────────────────────
   正式项目已经实现检索展开                 现有硬上限实现仍需修正

  适合正式问答系统，但是否适合 T2Retrieval baseline 需要谨慎。

  ### 方案 C：父子结构，但只 embedding Child

  Parent：保存上下文，不生成向量
  Child：生成向量，负责召回
  命中后：通过 parent_id 返回 Parent

   优点                                缺点
  ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━  ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
   避免 Parent/Child 抢占同一候选池    Parent 本身不能直接召回
  ──────────────────────────────────  ────────────────────────────────
   embedding 成本低于双索引            标题或整体主题信息需注入 Child
  ──────────────────────────────────  ────────────────────────────────
   small-to-big 逻辑清楚               必须保证 parent 映射可用
  ──────────────────────────────────  ────────────────────────────────
   面试时容易解释                      T2 文档级评估仍需 doc 聚合

  这是我现在更推荐的正式项目方案。

  ## 四、T2Retrieval 的聚合策略取舍

  切块以后，qrels 仍然只认识原始 doc_id，所以必须把 chunk 分数聚合成文档分数。

  假设某文档有三个 chunk：

  doc-A:
    chunk-0 = 0.42
    chunk-1 = 0.87
    chunk-2 = 0.55

  ### Max pooling

  doc_score = max(chunk_scores) = 0.87

   优点                                    缺点
  ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━  ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
   与“一个相关片段即可证明文档相关”吻合    可能被一个偶然高分 chunk 影响
  ──────────────────────────────────────  ───────────────────────────────────────────────────
   简单、常见、容易解释                    需要扩大 chunk 候选池，否则相关文档可能没进入候选
  ──────────────────────────────────────  ───────────────────────────────────────────────────
   不会因为文档 chunk 多直接累加获利       忽略多个中等相关 chunk 的共同证据

  这是最适合作为第一版 baseline 的方案。

  ### Top-N mean

  doc_score = mean(top 2 chunk scores)

   优点                  缺点
  ━━━━━━━━━━━━━━━━━━━━  ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
   比 max 更稳定         对短文档不公平，需要处理 chunk 数不足
  ────────────────────  ───────────────────────────────────────
   能表达多个相关片段    参数 N 需要实验选择

  适合作为后续对照实验，不适合先作为唯一实现。

  ### Sum pooling

  doc_score = sum(chunk_scores)

  问题最大：长文档 chunk 更多，会天然占优势。不建议。

  ## 六、我建议的目标设计

  我建议把“正式 RAG”和“T2 评测”建立在同一个核心切块器上，但允许不同配置：

                          Shared Token-Aware Splitter
                         /                           \
  正式 RAG                                      T2Retrieval
  父子结构                                      单层 512-token chunk
  只 embedding Child                            每个 chunk embedding
  命中后返回 Parent                             max 聚合回 doc_id
  ES 混合检索                                   mmap/NumPy dense baseline

  这样做的理由：

  - 共用真正可靠的超长文本算法。
  - 正式系统展示 small-to-big 设计能力。
  - T2 baseline 保持简单，评估结果容易解释。
  - 不强行让评测脚本复制正式系统所有复杂度。
  - 能做清楚的消融实验：
      - 不切块 vs 512 chunk
      - 256/512/768 chunk
      - overlap 0%/10%/20%
      - max pooling vs top-N mean
      - dense-only vs hybrid/rerank
