# Child 还是 Parent rerank：真实案例与面试回答

> 本文用原始输入和逐题分数解释重排粒度的取舍。完整实验指标与运行契约见 [实验报告](../../evaluation/reports/generated/parent_rerank_20260922/report.md)。以下都是本地 T2 冻结基准的真实案例，不是构造样例。

## 先统一怎么看这些分数

- 三个 demo 均取自同一轮 `project` hybrid 候选池：固定 500 题、每题 Top-50 Child、同一个 BAAI/bge-reranker-base，模型长度上限 512。Parent 由历史缓存的全部兄弟 Child 按原坐标拼回。
- `Child score` 是旧实验对“问题＋该子块”的 CE 分数。`Child-mean/max` 只聚合进入该题候选池的 Child；未召回的兄弟块不参与计算，也不能补成零分。
- `Parent score` 是本轮对“问题＋完整父块”直接算出的 CE 分数。分数经过 sigmoid，但不是校准后的正确概率；评价改善要看排名和指标。
- 下文列出该 Parent 的**全部 Children**，按原文顺序标成 child_a、child_b……；这些字母仅方便阅读，真实 chunk_id 一并保留。未送排的 Child 明确记为“未评分”。
- 排名统一是文档级排名：文档取其候选父块的最高分。`Top-10 外` 表示历史结果只保存了前十名，不能据此编出精确名次。
- 三个 demo 的“提升/降低”统一比较 **Parent CE 与原来的 Child-mean**；Child-max 和不重排只作参考，不在案例分析中切换比较基线。
- 父块和子块全文来自历史解析缓存，保留原始错字、残缺代码和网页噪声；代码围栏仅用于展示，源文本中的语句不代表操作建议。

## 如何选择 Child rerank 还是 Parent rerank

### 判断顺序

1. **先看 Child 是否能够独立表达证据。** 如果主体、条件、解释经常落在兄弟块里，单独精排容易低估正确父块，Parent 或命中窗口值得对照。
2. **把聚合方式和输入粒度分别比较。** 至少保留不重排、Child-mean、Child-max、Parent CE；避免把 mean 的问题误认为 Child 粒度一定不行。
3. **检查 Parent 的信息密度和模型实际长度。** 本轮 Child 输入对平均约 65 Token，Parent 约 170；只有 0.40% 的 Parent 输入对超出 512。长父块、跨主题正文、网页噪声和残缺代码都需要单独观察。
4. **固定候选集合和模型，先比较质量，再比较成本。** 看 Recall@5、MRR、nDCG 和逐题得失；另行实测同硬件、同批量、无缓存条件的重排延迟和最终回答质量。Parent 去重后候选数减少不等于推理一定更快。
5. **在独立数据上确认选择。** 这 500 题是已使用过的冻结基准，不是新留出集；本轮支持把 Parent rerank 作为候选改进，不能宣称它在所有语料上最优。若 Parent 太长，可进一步测试锚定 Child 的窗口重排，但本轮未做该实验。

### 面试口述回答（约 2～3 分钟）

> 我会先看检索片段是否能独立表达一个答案，以及父块展开以后增加的是必要上下文，还是无关内容，再用固定候选池做对照。
>
> 我最开始使用 Child 做召回和重排，然后按 Parent 聚合。这样每个重排输入比较短，但我实际分析后发现了两个问题。一个是均值聚合会稀释强命中：某个子块已经非常相关，另外几个较弱命中却把父块平均分拉低了。另一个是 Child 只适合作为检索入口，答案的主体或者解释在兄弟块里，单看它会低估相关性。
>
> 所以我固定同一批 500 道题、相同候选集合和同一个 BGE 重排模型，比较了 Child-mean、Child-max 和 Parent 直接重排。文档级 Recall@5 分别是 71.56%、72.89% 和 74.15%。这说明收益有一部分来自聚合方式，完整父块评分还带来了额外改善。Parent 相比原方案提升约 2.59 个百分点，配对置信区间没有跨零。
>
> 一个具体例子是查询哪些工厂在招工。召回的 Child 只有时薪和骗局的引言，父块里才有具体工厂和招工情况。这个父块只命中了一个子块，所以它的改善不能用均值聚合来解释，补上下文确实是值得考虑的方向。
>
> 但我也保留了失败案例。一个 Oracle 字符计数问题，子块里已经有明确的计算思路，展开父块以后混入残缺代码和网页页脚，金标文档反而从第一名掉到第八名，而且没有发生长度截断。所以我不会说父块越完整就一定越好，也不会把网页噪声直接当成已经证实的唯一原因。
>
> 对我这批相对短的父块，实验支持优先继续验证 Parent rerank；如果子块本身已经完整、父块噪声多或者容易超长，我也会保留 Child-max 或命中窗口作为候选。最终选择要同时看独立数据上的排序质量、真实延迟和回答效果。这轮我验证的是重排组件，还没有直接替换生产默认方案。

### 避免说错的四句话

- 不说“父块得分更高，所以效果更好”：最终看排序与金标，分数不是正确概率。
- 不说“提升全部来自更多上下文”：Child-max 的诊断组也有收益。
- 不说“父块改善了召回池”：候选父块和文档集合保持不变，改变的是最终排序。
- 不说“父块重排一定更快、答案一定更准”：这轮未做匹配条件的延迟对照，也未评生成质量。
