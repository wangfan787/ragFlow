## 〇、先用一个比喻建立全局观

把 RAG 想象成"开卷考试"：

- **Parse（解析）**：把一整本书拆成一张张卡片，每张卡片写清楚
  "这段话是标题还是正文、属于哪一章、在原书第几行第几个字"。
- **Chunk（切块）**：把卡片按字数重新装订成大小合适的册子。
- **Embedding（向量化）**：给每本册子做一张"内容索引卡"，方便以后按意思查找。
- **检索/引用**：考试时先查索引卡找到册子，翻开作答，并注明"出自原书第几页"。

**Parse 的职责边界**：只负责"结构"和"住址"，不管"切多碎"（那是 chunk 的事），
也不管"什么意思"（那是 embedding 的事）。面试时主动说清这个边界，是加分项。

## 一、主流 RAG 对各格式的 parse 处理

### 1. Markdown —— 结构是白送的

Markdown 的结构是**写在上面的**（`#` 是标题、`-` 是列表、``` 是代码块），
所以主流做法就是"用语法解析器直接读"：

- 通用做法：按语法树把文档拆成"标题 + 它管辖的内容"，并**保留标题层级**
  （比如 `["第二章", "2.1 小节"]`，像面包屑导航）。
- 关键细节：
  - 代码块、表格**不能被切碎**（里面的 `#`、`|` 不是语法）；
  - 标题层级要随开合正确进退栈（遇到 `###` 再遇到 `#`，层级要弹回去）；
  - 记录每个块在原文的位置，方便引用。
- 主流工具：LangChain 的 `MarkdownHeaderTextSplitter`、LlamaIndex 的 `MarkdownNodeParser`，
  思路都是"按标题切 + 带层级路径"。

**我的项目**：用 `markdown-it-py`（一个标准的 Markdown 语法解析库，比手写正则可靠），
维护标题栈生成 `section_path`，把解析器给出的行号换算成全文绝对坐标。
（代码：`markdown_parser_it.py`，全库最大的 parser，366 行——Markdown 的规则比看起来多。）

### 2. HTML —— 关键是"扔对东西"

HTML 里混着三种东西：**内容**（正文段落、标题）、**噪音**（script 脚本、style 样式、
导航栏、广告）、**容器**（div/span 这些只负责排版不负责含义的标签）。主流分两派：

- **简单派**：把所有标签撕掉只留文字。快，但标题层级、段落边界全没了，
  且容易把菜单栏文字混进正文。
- **结构派**（主流）：先删掉 script/style 这类必然不是正文的标签，
  再只挑"有含义的标签"（`h1~h6`、`p`、`li`、`table`、`pre`）逐个提取成块。
  代表：Unstructured 的 `partition_html`、LangChain 的 `HTMLHeaderTextSplitter`。

关键细节：
- 标签删掉后文字会"拼接变样"（多余空格、实体字符 `&amp;` → `&`），要清洗；
- 清洗之后，"现在的文字"和"原始网页文字"对不上号了——讲究的做法会记一张
  **映射表**（清洗后的第几段 ↔ 原文第几个字）；
- `<img>` 这类没有文字的标签：主流直接跳过，或者取它的 alt 说明文字。

**我的项目**：结构派。BeautifulSoup 删 `script/style/noscript`，白名单标签逐个提取，
顺带处理了"散落在容器标签里的裸文字"；清洗后生成 `normalization_segments` 映射表，
定位失败时诚实降级精度标注。
（代码：`html_parser.py`。T2 评测里 64.8% 的文档走的就是这个 parser。）

### 3. PDF —— 公认最难的，难点要能讲清楚

**为什么 PDF 难**：PDF 内部存的不是"文章"，而是**绘图指令**——
"在第 3 英寸、第 5 英寸的位置，画上这些字形"。它根本没有"段落""标题"的概念，
双栏排版、表格线、扫描图片在数据层面统统不存在。所以 PDF 解析天然分三档：

| 档位 | 做法 | 能处理 | 代价 |
|---|---|---|---|
| ① 文本层直读 | 用库（pypdf / pdfplumber / PyMuPDF）把文字按顺序读出来 | 文字版、排版简单的 PDF | 双栏会串行、表格变乱码、扫描件完全读不出 |
| ② 版面分析 | 先用模型识别"这是标题/段落/表格/图片框"，再按框提取 | 复杂排版、表格 | 要跑模型，工程重 |
| ③ OCR / 视觉模型 | 扫描件先转图再认字（PaddleOCR、Tesseract），或直接用视觉大模型读页 | 扫描件、截图 | 最重、最贵 |

**主流工具**（面试报得出名字即可）：
- **RAGFlow 自研 DeepDOC**：②+③ 的组合，工业级但工程很重；
- **MinerU / Marker / Docling**：开源的"PDF 转 Markdown"全家桶（版面模型 + OCR）；
- **LlamaParse**：LlamaIndex 的商业解析 API（花钱买省事）。

**我的项目**：只做了第①档（pypdf 文本直读），并在文档里**明确声明边界**：
不支持扫描件和复杂表格，`bbox`（版面框坐标）留了字段但没实现。
这是个人项目的主动取舍——把力气花在检索主链路上，而不是和 PDF 排版搏斗。

### 4. 纯文本 —— 没结构就是结构

纯文本没有任何标记，唯一可依赖的排版信号是**空行**（作者用空行分段）。
主流做法都是"按空行/换行切段 + 记录字符位置"，没什么花活。

**我的项目**：按空行正则切段，字符级 `exact` 坐标。
（代码：`text_parser.py`，全库最短的 parser，52 行——格式越朴素，parser 越短。）

## 二、不同格式最终要长成一个模样

面试高频追问："四种格式四个 parser，后面四套代码吗？"
正确答案：**不。parse 层的第一原则是输出统一。**

我的项目里所有 parser 的输出都是同一个结构（LangChain Document）：

```
每个块 =
  page_content : 正文文字
  metadata     : {
    block_type      ← 我是什么（标题/段落/代码/表格/列表）→ 决定下游怎么切
    section_path    ← 我属于哪一章哪节（面包屑）→ 用于展示和引用
    source_span     ← 我在原文的哪几行哪几个字 → 用于引用溯源
    accuracy        ← 这个坐标多可信（精确/只有行级/不可用）→ 不伪造精度
    order           ← 我是第几个块 → 保住阅读顺序
    page_no / bbox  ← PDF 页码 / 版面框（预留）
    normalization_segments ← (仅 HTML) 清洗后文字 ↔ 原文 的对照表
  }
```

这样做的直接收益（都是我真实跑出来的场景）：
- 评测数据集里 64.8% 的 HTML 文档和 35.2% 的纯文本文档，**走的是同一条**
  分块 → 向量化 → 检索链路，一行格式判断代码都不用出现在下游；
- 引用（citation）可以精确回溯到原文——曾手工验算过 HTML 解析输出的字符坐标，
  与原文逐字吻合（比如两个块之间的坐标缺口正好是 4 个字符的 `<br>` 标签）。

## 三、"我的 parse 差在哪、好在哪"（诚实版对比）

| 维度 | LangChain/Unstructured | RAGFlow | 我的项目 |
|---|---|---|---|
| Markdown/HTML | 有现成 splitter | 有 | 有，且带原文坐标和精度标注 |
| PDF 复杂版面 | 一般 | **DeepDOC，工业级** | 只有文本直读（明确声明局限） |
| 扫描件/OCR | 部分支持 | 支持 | 不支持（声明了） |
| 输出契约 | 各家不同（多为纯文本段） | 松散 dict | **强类型统一 block + 溯源字段全链路透传** |
| 适合场景 | 快速原型 | 企业级文档池 | 个人项目、检索主链路优先 |

一句话总结（可直接背）：
**"我把工程力气花在'结构统一 + 位置可溯源'上，把 PDF 重版面这类重活明确划出边界；
因为我的评测证明，检索质量的主要矛盾在分块和召回，不在 PDF 版面。"**

## 四、面试 QA（背这 15 问）

**Q1：讲讲你的文档解析流程。**
> 输入统一成一个 ParseSource（文件路径或内存文本都行，严格 UTF-8）；
> 工厂按文件类型路由到四个解析器：Markdown 用 markdown-it-py 语法解析、
> HTML 用 BeautifulSoup 白名单提取、纯文本按空行分段、PDF 用 pypdf 直读；
> 输出统一成带结构字段的 block：类型、章节路径、原文坐标、精度标注。
> 下游切块器只认这套 block，完全不关心来源格式。

**Q2：为什么解析和切块要分开？**
> 职责不同：解析管"结构和住址"（这是什么、在原文哪里），
> 切块管"长度"（切多碎才适合向量检索）。分开后格式差异在解析层就终结了，
> 新增一种格式只需加一个 parser，切块及其下游一行不用改。
> 我评测时 65% HTML + 35% 纯文本混着走同一条链路，就是这么来的。

**Q3：HTML 里 script、style 怎么处理？图片呢？**
> script/style/noscript 直接整棵删掉——它们永远不是正文；
> 只从有含义的标签（标题/段落/列表/表格/代码）提取；
> `<img>` 没有文字就跳过。删标签会让文字变样，所以我记了一张
> 清洗后文字到原文的映射表，引用时能反查回原始网页。

**Q4：PDF 扫描件你的方案支持吗？**
> 不支持，这是明确声明的边界。我用的 pypdf 只能读"文字层"PDF，
> 扫描件本质是图片，需要 OCR 或版面模型（RAGFlow 的 DeepDOC、开源的 MinerU
> 就是干这个的）。个人项目我把力气花在检索主链路；真要支持，
> 接入 MinerU 这类现成方案比自研划算。

**Q5：表格怎么处理的？**
> Markdown 和 HTML 的表格会作为独立的"表格块"整体提取，切块时优先保持完整；
> 超过硬上限时才允许切，并记录接续关系。但表格**内部结构**（哪行哪列）
> 我没有解析——表格对向量检索来说就是一段文本，这是当前边界。

**Q6：为什么要费劲记录原文坐标？直接切了不行吗？**
> 因为 RAG 的答案要能溯源。我的 citation 能告诉用户"这条证据来自原文
> 第几行第几个字"，靠的就是解析层写下的 span 坐标，然后一路透传：
> 解析 → 分块 → 索引 → 检索 → 引用，任何一层丢了坐标，溯源就断了。

**Q7：坐标为什么还有"可信度"标注？**
> 因为文本被清洗过后（HTML 删标签、Markdown 去记号），字符位置可能不再精确。
> 我分三档：exact（字符级精确）、line_only（只保证行级）、unavailable（定位失败）。
> 原则是宁可保守降级也不伪造精确——引用系统说"在第 3 行"就必须真在第 3 行。

**Q8：Markdown 为什么用现成解析库而不用正则？**
> 我两种都写过（项目里就留着旧的正则版做对照测试）。正则版在嵌套代码块、
> 不规范表格上漏洞百出——`代码块里的 #` 不是标题。markdown-it-py 是标准
> 语法解析器，这类坑它都处理了。教训：**结构化文本用结构化解析器，别用正则硬扛。**

**Q9：你的解析和 RAGFlow 比差在哪？**
> PDF 重版面（DeepDOC 的版面模型 + OCR）是我明确不做的，那是它企业级文档池
> 的核心投入；我的优势是输出契约更严格——强类型统一 block、坐标和精度标注
> 全链路透传到引用。个人项目先把检索主链路跑通做对，重活明确划边界。

**Q10：如果让你新增 Word/PPT 支持，怎么改？**
> 只需新增一个 parser：用 python-docx / python-pptx 把标题、段落、表格提取成
> 和现有格式一样的 block 结构（类型 + 章节路径 + 坐标），注册进工厂路由。
> 切块、向量化、检索、引用全链路零改动——这就是统一输出契约的价值。

**Q11：解析阶段会丢信息吗？**
> 会，我知道丢什么：HTML 的图片（除非取 alt 文字）、PDF 的版面和扫描内容、
> 表格的单元格结构。原则是"丢要丢得明明白白"——每条边界都写进了设计文档，
> 不假装支持。比"默默丢"更危险的是"不知道自己在丢"。

**Q12：怎么验证你的解析是对的？**
> 三层：单元测试盯语法细节（嵌套代码块、GFM 表格、非法 UTF-8）；
> 一个"可视化展示测试"用真实数据集文档把输入输出整个打出来人工核对；
> 以及数学验证——我曾手工验算 HTML 输出的字符坐标，块与块之间的坐标缺口
> 正好等于被删掉的 `<br>` 标签长度，逐块吻合。

**Q13：LangChain 有现成的解析/切分器，你为什么不用？**
> 分格式回答。Markdown 和 HTML：LangChain 确实内置了结构感知切分器——
> `MarkdownHeaderTextSplitter`、`HTMLHeaderTextSplitter`/`HTMLSectionSplitter`，
> 思路和我的 section_path 一样（按标题切 + 层级路径进 metadata）。
> PDF：LangChain **没有**结构感知切分器，只提供各种 Loader（PyPDF、
> PyMuPDF、Unstructured、OCR 的 Textract、对接 Docling 等），提取完退回
> 通用的 RecursiveCharacterTextSplitter——因为 PDF 在数据层面只有坐标和字形，
> 根本没有结构可感知，结构解析必须外包给版面模型/OCR 专业引擎。
> 我的差异点：HTML 切分器里我比 LangChain 多做了字符级坐标 + 精度降级标注 +
> 清洗映射表（它的切分器切完就丢原文坐标）；PDF 我和它的默认路径同级，
> 但我把"不支持扫描件"写成了明确声明而不是默认行为。

**Q14：字符级坐标、精度降级标注、清洗映射表，具体是什么？**
> 用一篇原文 `<p>锁是控制并发访问的工具</p><p>锁有三种</p>` 举例：
>
> - **字符级坐标**（source_span 的 start_char/end_char）：撕掉标签后手里是干净文字
>   "锁是控制并发访问的工具"，但它原本夹在原文的第 3~15 个字符之间——这个"住址"
>   记在 source_span 里。没有它，引用只能说"证据大概在这篇文档里"；有了它，
>   前端才能精确高亮原文那一段。
> - **精度降级标注**（accuracy 三档）：撕标签不是无损操作，反查原文位置
>   有时精确、有时只能到行、有时找不到。分 exact（精确到门牌号）/
>   line_only（只到小区）/ unavailable（地址丢了）三档。不标注的话系统会
>   默认所有坐标都精确，指错了都不知道；标了档位，下游能做策略——
>   exact 才逐字高亮，line_only 只跳到行。
> - **清洗映射表**（normalization_segments）："清洗后第 0~16 字 = 原文第 0~16 字"
>   的对照账本。清洗越狠（删的标签越多）越重要，是把洗过的正文逐段对回
>   原始网页的依据。
>
> 三者关系一句话：**坐标是住址，精度标注是住址的可信等级，映射表是打扫过的
> 房间与原样的对照账本。** LangChain 的 HTMLHeaderTextSplitter 之所以没有，
> 是因为它的产出只有"切块 + 标题路径"，切完就和原文告别了——压根没设计"回原文"。

**Q15：既然 LangChain 有现成的，Markdown 解析能换成它的版本吗？**
> 可以换，但换的是错的东西——两者解决的不是同一个问题。
>
> | | MarkdownHeaderTextSplitter | 我的 markdown_parser_it |
> |---|---|---|
> | 本质 | 切块器（解析+切分合体） | 解析器（只管变 block，切多碎不归它管） |
> | 输出 | "某标题下的全部内容"一片 | block，带 block_type/source_span/accuracy |
> | 原文坐标 | ❌ | ✅ |
>
> 换过去会连环丢三样：① block_type 没了 → chunker 的 heading 边界、
> 代码/表格保护失效；② source_span 没了 → citation 从源头断链；
> ③ 统一契约破了 → md 要走特判，或绕过评测验证过的严格切分和覆盖守恒校验。
>
> 若被追问"那你不怕重复造轮子？"：markdown-it-py 本身就是现成轮子
> （语法解析我没自己写），自研的只是 366 行"语法树 → 统一 block + 坐标"的
> 胶水层，这层是项目契约特有的，没有现成的。反过来说，如果需求只是
> "单格式、不要溯源、快速出活"，用 LangChain 的 splitter 才是正确选型——
> **选型取决于需求，不是越重越好。**

## 五、三个可以主动抛出的加分点

1. **"解析的职责边界"意识**：主动区分 parse（结构+住址）/ chunk（长度）/
   embedding（语义），并说明格式差异应在 parse 层终结——这体现系统设计能力。
2. **"诚实降级"设计**：坐标三档精度 + 清洗映射表，宁可标"不可用"不伪造精确
   ——这体现工程诚信，面试官通常会追问"为什么不直接都标精确"，答：
   "引用系统的可信度取决于最上游的诚实度"。
3. **用数据说话**：评测集里 64.8% HTML / 35.2% 纯文本走同一条链路、
   坐标手工验算逐字吻合、新旧解析器对照测试——都是现成可演示的证据。
