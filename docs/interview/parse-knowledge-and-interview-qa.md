> 目标读者：准备面试的自己。
> 原则：先讲人话，再对照自己项目的代码；术语第一次出现都带解释。
> 配套代码：`backend/src/parsing/`；当前实现核对日期：2026-09-23。

## 〇、先用一个比喻建立全局观

把 RAG 想象成"开卷考试"：

- **Parse（解析）**：把一整本书拆成一张张卡片，每张卡片写清楚
  "这段话是标题还是正文、属于哪一章、在原书第几行第几个字"。
- **Chunk（切块）**：把卡片按字数重新装订成大小合适的册子。
- **Embedding（向量化）**：给每本册子做一张"内容索引卡"，方便以后按意思查找。
- **检索/引用**：考试时先查索引卡找到册子，翻开作答，并注明"出自原书第几页"。

**Parse 的职责边界**：只负责"结构"和"住址"，不管"切多碎"（那是 chunk 的事），
也不管"什么意思"（那是 embedding 的事）。面试时主动说清这个边界，是加分项。

## 一、主流 RAG 对各格式的 parse 处理

### 1. Markdown —— 结构是白送的

Markdown 的结构是**写在上面的**（`#` 是标题、`-` 是列表、``` 是代码块），
所以主流做法就是"用语法解析器直接读"：

- 通用做法：按语法树把文档拆成"标题 + 它管辖的内容"，并**保留标题层级**
  （比如 `["第二章", "2.1 小节"]`，像面包屑导航）。
- 关键细节：
  - 代码块、表格**不能被切碎**（里面的 `#`、`|` 不是语法）；
  - 标题层级要随开合正确进退栈（遇到 `###` 再遇到 `#`，层级要弹回去）；
  - 记录每个块在原文的位置，方便引用。
- 主流工具：LangChain 的 `MarkdownHeaderTextSplitter`、LlamaIndex 的 `MarkdownNodeParser`，
  思路都是"按标题切 + 带层级路径"。

**我的项目**：统一入口是 `UnstructuredParser`。先由 `markdown_structures.py` 用
`markdown-it-py` 识别代码和表格，保存原文、精确坐标并替换成占位段落；
其余内容交给 `partition_md`，随后恢复受保护结构，根据元素标题深度生成 `section_path`。
普通文本通过回定位获得来源，不能可靠定位时降低精度；frontmatter 单独保留。

### 2. HTML —— 关键是"扔对东西"

HTML 里混着三种东西：**内容**（正文段落、标题）、**噪音**（script 脚本、style 样式、
导航栏、广告）、**容器**（div/span 这些只负责排版不负责含义的标签）。主流分两派：

- **简单派**：把所有标签撕掉只留文字。快，但标题层级、段落边界全没了，
  且容易把菜单栏文字混进正文。
- **结构派**（主流）：先删掉 script/style 这类必然不是正文的标签，
  再只挑"有含义的标签"（`h1~h6`、`p`、`li`、`table`、`pre`）逐个提取成块。
  代表：Unstructured 的 `partition_html`、LangChain 的 `HTMLHeaderTextSplitter`。

关键细节：
- 标签删掉后文字会"拼接变样"（多余空格、实体字符 `&amp;` → `&`），要清洗；
- 清洗之后，"现在的文字"和"原始网页文字"对不上号了——讲究的做法会记一张
  **映射表**（清洗后的第几段 ↔ 原文第几个字）；
- `<img>` 这类没有文字的标签：主流直接跳过，或者取它的 alt 说明文字。

**我的项目**：由 Unstructured 的 `partition_html` 提取元素，再统一映射为 block。
表格优先保留引擎提供的 `text_as_html`。普通文本回定位前会解码实体，
定位成功标为 `line_only`，失败标为 `unavailable`，不承诺原始 HTML 的逐字符高亮。
当前没有输出 `normalization_segments` 映射表，也没有自写的 HTML 白名单解析器。

### 3. PDF —— 公认最难的，难点要能讲清楚

**为什么 PDF 难**：PDF 内部存的不是"文章"，而是**绘图指令**——
"在第 3 英寸、第 5 英寸的位置，画上这些字形"。它根本没有"段落""标题"的概念，
双栏排版、表格线、扫描图片在数据层面统统不存在。所以 PDF 解析天然分三档：

| 档位 | 做法 | 能处理 | 代价 |
|---|---|---|---|
| ① 文本层直读 | 用库（pypdf / pdfplumber / PyMuPDF）把文字按顺序读出来 | 文字版、排版简单的 PDF | 双栏会串行、表格变乱码、扫描件完全读不出 |
| ② 版面分析 | 先用模型识别"这是标题/段落/表格/图片框"，再按框提取 | 复杂排版、表格 | 要跑模型，工程重 |
| ③ OCR / 视觉模型 | 扫描件先转图再认字（PaddleOCR、Tesseract），或直接用视觉大模型读页 | 扫描件、截图 | 最重、最贵 |

**主流工具**（面试报得出名字即可）：
- **RAGFlow 自研 DeepDOC**：②+③ 的组合，工业级但工程很重；
- **MinerU / Marker / Docling**：开源的"PDF 转 Markdown"全家桶（版面模型 + OCR）；
- **LlamaParse**：LlamaIndex 的商业解析 API（花钱买省事）。

**我的项目**：只做了第①档（Unstructured `fast`，底层为 pdfminer 文本抽取），并**明确声明边界**：
不支持扫描件和复杂表格，`bbox`（版面框坐标）留了字段但没实现。
这是个人项目的主动取舍——把力气花在检索主链路上，而不是和 PDF 排版搏斗。

### 4. 纯文本 —— 没结构就是结构

纯文本没有任何标记，唯一可依赖的排版信号是**空行**（作者用空行分段）。
主流做法都是"按空行/换行切段 + 记录字符位置"，没什么花活。

**我的项目**：调用 `partition_text`，把所有元素统一按普通段落处理，避免短句被误判成标题。
只有原文切片与输出逐字一致才标为 `exact`；其余按定位结果降级。

## 二、不同格式最终要长成一个模样

面试高频追问："四种格式，后面要四套代码吗？"
正确答案：**不。当前四种格式共用一个解析器，格式差异在 partition 调用和适配层处理。**

我的项目里所有 parser 的输出都是同一个结构（LangChain Document）：

```
每个块 =
  page_content : 正文文字
  metadata     : {
    block_type      ← 我是什么（标题/段落/代码/表格/列表）→ 决定下游怎么切
    section_path    ← 我属于哪一章哪节（面包屑）→ 用于展示和引用
    source_span     ← 我在原文的哪几行哪几个字 → 用于引用溯源
    source_span.accuracy ← 坐标可信度（精确/只有行级/不可用）→ 不伪造精度
    order           ← 我是第几个块 → 保住阅读顺序
    page_no / bbox  ← PDF 页码 / 版面框（bbox 当前为 None）
  }
```

这样做的直接收益：
- 不同格式共享分块 → 向量化 → 检索链路，下游不必为每种格式重复实现算法；
- 引用保留来源及精度，只有 `exact` 才支持逐字定位，不能把 HTML 的行级结果当成精确字符坐标。

历史 T2 v2 实验中，语料为 64.8% HTML、35.2% 纯文本；它证明过统一契约的可用性，
不能作为当前 v3 解析/分块策略已经全量重跑的证据。

## 三、"我的 parse 差在哪、好在哪"（诚实版对比）

| 维度 | LangChain/Unstructured | RAGFlow | 我的项目 |
|---|---|---|---|
| Markdown/HTML | 有现成 splitter | 有 | 有，且带原文坐标和精度标注 |
| PDF 复杂版面 | 一般 | **DeepDOC，工业级** | 只有文本直读（明确声明局限） |
| 扫描件/OCR | 部分支持 | 支持 | 不支持（声明了） |
| 输出契约 | 各家不同（多为纯文本段） | 松散 dict | **强类型统一 block + 溯源字段全链路透传** |
| 适合场景 | 快速原型 | 企业级文档池 | 个人项目、检索主链路优先 |

一句话总结（可直接背）：
**"我把工程力气花在'结构统一 + 位置可溯源'上，把 PDF 重版面这类重活明确划出边界；
当前检索基准以文本为主，没有覆盖复杂 PDF，不能用它证明 PDF 版面不影响质量。"**

## 四、面试 QA（背这 15 问）

**Q1：讲讲你的文档解析流程。**
> 输入统一成 ParseSource：文本格式支持文件或内存文本，文件按严格 UTF-8 读取，PDF 走文件路径；
> 工厂校验类型后返回 UnstructuredParser，内部调用各格式的 partition 方法。
> Markdown 额外用 markdown-it-py 保护代码和表格原文，PDF 采用 fast 文本抽取；
> 输出统一成带结构字段的 block：类型、章节路径、原文坐标、精度标注。
> 下游切块器只认这套 block，完全不关心来源格式。

**Q2：为什么解析和切块要分开？**
> 职责不同：解析管"结构和住址"（这是什么、在原文哪里），
> 切块管"长度"（切多碎才适合向量检索）。分开后格式差异在解析层就终结了，
> 新格式适配到同一 block 契约后，可以复用下游；仍要验证结构和来源字段是否满足约束。
> 历史 T2 v2 实验中约 65% HTML、35% 纯文本共享同一条下游链路。

**Q3：HTML 里 script、style 怎么处理？图片呢？**
> 当前把 HTML 内容提取交给 partition_html，再把元素映射为统一 block，
> 不维护自写的标签白名单。HTML 图片没有进入资产/VLM 主链。
> 文本经过规范化后通过回定位补来源，成功也只标行级精度；当前没有输出清洗映射表。

**Q4：PDF 扫描件你的方案支持吗？**
> 不支持，这是明确声明的边界。当前 Unstructured fast 路径只抽取 PDF 文字层，
> 扫描件本质是图片，需要 OCR 或版面模型（RAGFlow 的 DeepDOC、开源的 MinerU
> 就是干这个的）。个人项目我把力气花在检索主链路；真要支持，
> 接入 MinerU 这类现成方案比自研划算。

**Q5：表格怎么处理的？**
> Markdown 表格按语法边界保留原文；HTML 等格式优先使用引擎返回的 text_as_html。
> 默认一张表对应独立 Parent 和同内容的一个 Child，豁免普通正文的 192 token 预算。
> 嵌入仍受模型上限约束，当前默认按 cl100k_base 估算 3072 token；超限报错，不静默截断。
> 关闭 preserve_table_block 才按普通正文切分。当前没有单元格级查询或表格推理能力。

**Q6：为什么要费劲记录原文坐标？直接切了不行吗？**
> 因为 RAG 的答案要能溯源。我的 citation 携带来源范围和精度，按可信程度定位到字符、行或页，
> 靠的就是解析层写下的 span 坐标，然后一路透传：
> 解析 → 分块 → 索引 → 检索 → 引用，任何一层丢了坐标，溯源就断了。

**Q7：坐标为什么还有"可信度"标注？**
> 因为文本被清洗过后（HTML 删标签、Markdown 去记号），字符位置可能不再精确。
> 我分三档：exact（字符级精确）、line_only（只保证行级）、unavailable（定位失败）。
> 原则是宁可保守降级也不伪造精确——引用系统说"在第 3 行"就必须真在第 3 行。

**Q8：Markdown 为什么用现成解析库而不用正则？**
> 因为代码里的 #、表格里的竖线和嵌套列表不能只靠一条正则区分。
> 当前用 markdown-it-py 的语法边界保护代码/表格，再交给统一引擎处理其余内容；
> 旧自写解析器已删除，回归测试直接约束现有实现。结构化文本优先用语法解析器。

**Q9：你的解析和 RAGFlow 比差在哪？**
> PDF 重版面（DeepDOC 的版面模型 + OCR）是我明确不做的，那是它企业级文档池
> 的核心投入；我的工程重点是统一 block、坐标和精度标注
> 全链路透传到引用。个人项目先把检索主链路跑通做对，重活明确划边界。

**Q10：如果让你新增 Word/PPT 支持，怎么改？**
> 先扩展上传白名单与解析工厂的支持类型，再选择对应的 partition 或专用适配器，
> 输出同一 block 契约。随后验证标题、表格、页码和坐标降级行为，补依赖与样例测试。
> 下游可复用，但不能省略契约验证，也不能承诺新格式一定有字符级坐标。

**Q11：解析阶段会丢信息吗？**
> 会，我知道丢什么：HTML 的图片（除非取 alt 文字）、PDF 的版面和扫描内容、
> 引擎未保留的表格结构。Markdown 原表格与可得的 HTML 表格结构会保留，
> 但没有单元格级理解。原则是"丢要丢得明明白白"——每条边界都写进了设计文档，
> 不假装支持。比"默默丢"更危险的是"不知道自己在丢"。

**Q12：怎么验证你的解析是对的？**
> 测试覆盖嵌套代码、Markdown 表格原文、非法 UTF-8、HTML 实体和重复文本定位；
> 跨层回归验证 Parent/Child 内容守恒、预算和来源坐标投影。
> 测试入口是 backend/tests/parsing 与 backend/tests/chunking；人工演示可用
> backend/scripts/demo/walkthrough_demo.py。测试通过和真实 ES/模型联调分别记录。

**Q13：LangChain 有现成的解析/切分器，你为什么不用？**
> 我已经复用了现成引擎：Unstructured 负责内容提取，markdown-it-py 负责结构识别，
> LangChain Document 作为统一载体。项目自己维护的是元素到 block 的适配、
> 来源精度、父子块预算、结构保护和引用契约。
> 直接接一个通用 splitter 之前，要确认它能保留这些字段和不变量，不能只看是否能切出文本。

**Q14：来源坐标和精度降级标注，具体是什么？**
> source_span 保存 start_char/end_char、行范围、页码和 accuracy。
> 例如 Markdown 受保护的代码块直接按语法行号截取原文，坐标可标 exact；
> 普通 Markdown/HTML 文本经过规范化再回定位，成功也只标 line_only；
> PDF 当前保留可得页码，字符定位标 unavailable。
> exact 才支持逐字符高亮，line_only 只承诺行级定位，unavailable 不画假高亮。
> 内部回定位的辅助下标不等于对外的清洗映射表，当前不输出 normalization_segments。

**Q15：既然 LangChain 有现成的，Markdown 解析能换成它的版本吗？**
> 可以评估，但当前换的是 UnstructuredParser 加结构保护适配层。
> 不能只把按标题切好的文本直接塞给下游：需要补齐 block_type、source_span、
> 精度和结构保留策略，再通过相同的分块守恒与引用回归。
> 如果只需要单格式文本问答，标题 splitter 很方便；我的项目还要求多格式统一、
> 父子预算和来源追踪，所以采用现成解析引擎加项目适配层。

## 五、三个可以主动抛出的加分点

1. **"解析的职责边界"意识**：主动区分 parse（结构+住址）/ chunk（长度）/
   embedding（语义），并说明格式差异应在 parse 层终结——这体现系统设计能力。
2. **"诚实降级"设计**：坐标三档精度，宁可标"不可用"不伪造精确
   ——这体现工程诚信，面试官通常会追问"为什么不直接都标精确"，答：
   "引用系统的可信度取决于最上游的诚实度"。
3. **用验证说话**：展示当前结构保留、重复文本定位和分块守恒测试；
   引用历史 T2 v2 数据时带上版本，不把旧解析器的表现算到当前实现上。
