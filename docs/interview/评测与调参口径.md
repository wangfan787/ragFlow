父子粒度重排的真实原文、逐块分数和选型回答见 [Child 还是 Parent rerank：真实案例与面试回答](child-parent-rerank-cases.md)。这是独立的 T2 冻结候选池实验，与下文 CRUD-RAG 问答评测分开理解。

## 评测集口径（30 秒版本）

> 我从 CRUD-RAG 固定构建了 1,000 篇文档和 150 条分层问答，1/2/3 文档问题各 50 条，Dev 30 条调参、Test 120 条验收，按事件 ID 隔离，并固定上游 commit、随机种子和文件哈希。首次真实实验使用生产链路 Runner，单变量扫描后锁定配置，Test Recall@10 为 97.5%，证据文档召回为 93.1%，引用有效率为 96.7%，P95 延迟约 2.3 秒。效果指标可以离线复算，历史全程成本估算约 ¥2。这是受控 Mini Benchmark，不等价于线上效果，语义回答质量仍需经过人工校准的 Judge 评估。

## 调参故事：一分钟版本（先背这个）

> 第一次真实评测时，默认混合检索在 Dev 上的召回反而比纯向量低约 9 个百分点。我先比较单通道，发现 BM25 本身的总体召回不低，于是检查融合和父块聚合：两路分数归一化后加权，候选池变化也会改变参与父块均值的子块集合，因此混合不保证更好。我在 Dev 上单变量扫描，发现浅候选池、较高阈值和更多返回名额组合起来有效；扫权重没有超过默认结果，规则重排提高了召回却降低 MRR，没有满足预先设置的开启条件。锁定后在 120 道 Test 题上，召回从 88.2% 提高到 97.5%。回答侧选择 full_parent，历史引用有效率为 96.7%、P95 约 2.3 秒。这里验证的是配置组合改善，归一化是不是唯一根因，还需要固定候选的进一步消融。

## 按追问展开

**Q：碰见了什么问题？**
默认参数下 hybrid Recall@10 为 0.867，纯向量为 0.956（Dev 30 题）。混合检索没有自动获得互补收益，需要检查分数融合、父块聚合与最终截断。

**Q：怎么定位的？**

1. keyword 单通道 Recall@10 为 0.944，说明它在该子集总体不弱，但不排除逐题误召回。
2. 代码中 BM25 按本题最高分归一，正分头名在默认权重下贡献 0.25；这可能改变融合顺序，但不能据此断言它必然是错文档。
3. 池深 10/30/50/100 对应 0.944/0.867/0.822/0.889：10 到 50 下降，100 时回升，**不是单调关系**。
4. 因为池深还影响命中 Child 的父块聚合组成，这些结果支持浅池选型，没有隔离出唯一根因。

**Q：尝试了什么方法？**

1. 池子 30→10、阈值 0.1→0.2、返回名额 5→10，组合配置在 Dev 复验、Test 验收均提高召回。
2. 扫描 6 档融合权重，Recall 在 0.84～0.87，没有超过默认结果；这是本轮扫描结论，不表示权重永远无用。
3. 规则重排令 Recall 增加约 5.6pp、MRR 降低约 3.6pp，未达到“Recall 增益至少 1pp 且 MRR 不降”的预设开启条件。

**Q：怎么降低过拟合风险？**
只用 Dev 调参、一次改变一个参数，并预先规定选择标准；锁定后才运行 Test，不根据 Test 回调参数。Dev 只有 30 题，不能靠“看起来单调”就宣称机制成立。小差异应报告逐题变化和配对置信区间；后续实验改变选择标准时需要新的独立验收数据。

**Q：结果怎么验证的？**
锁定配置在 Dev 复验为 0.9722，Test 为 0.9750，默认 hybrid 为 0.8819、纯向量为 0.9236。按原始 run 与 qrels 逐题统计，默认 hybrid 到锁定配置增加了 25 个命中的问题—文档对（207→232），不能把宏平均召回差直接乘题数换算成文档数。历史回答实验完成了 120 题 × 3 种证据模式，零失败；full_parent 的证据文档召回为 93.1%、引用有效率为 96.7%、引用文档精度为 87.36%、P95 约 2.3 秒。

**Q：回答质量怎么评的？没用 LLM Judge 靠谱吗？**
先用确定性文档级指标：Evidence Recall 看正例文档是否进入证据集合；Citation Validity 看引用文档是否属于所给证据；Citation Document Precision 看引用文档是否属于正例。这些可复算，但不能证明证据片段包含答案，也不能证明每句话被引用支持。因此 96.7% 叫“引用有效率”，不叫语义层面的“引用正确率”。Faithfulness、Correctness 与逐条引用支持关系仍需人工校准的 Judge。

**Q：现在换成 RRF，之前的优化还能讲吗？**
能。表述为：“早期使用线性加权融合，发现默认混合检索不如纯向量，通过单变量调参和锁定验收改善了结果。后续将融合改成按名次计算的 RRF，减少对两路分数刻度的依赖；新版效果待重新评测。”不能说 RRF 带来了历史的 88.2%→97.5%，也不能说已经证明归一化是唯一根因。

当前 `rrf_score = Σ 1/(60+rank)`，未召回的一路贡献 0；`fused_score = rrf_score / (2/61)`，用固定理论上限缩放到 0～1，不改变排序。单通道保留原分数。缩放后仍不是相关概率，旧阈值与规则重排增益需要重测；旧锁定配置中的权重参数已不再被当前接口接受，历史 run 可继续离线复算。

**Q：这组参数能直接用到别的场景吗？**
需要重测。可复用的是基线比较、机制假设、单变量扫描、组合复验和锁定验收流程。换语料、模型或分块版本后，保留旧实验产物，再用同一 Runner 建立新基线。
