# 项目背景

版本：v1，2026-09-06。首版规格已写入 plan.md 和 8 个阶段文件；模型调用已替换，主链路已统一使用 Document，删除多套文本容器和重复转换。运行验证待 agent 环境；图片解析、md-v1 字段/索引、最终 API 等产物待实施。

## 用户的核心目标

这是用于秋招简历和面试的个人项目，时间紧，代码需要精简、便于理解和快速复习。用户使用 Codex 开发，希望新对话能根据文档直接实现，而不是每次重新讨论候选方案。

产品专注企业 Markdown 图文问答：文档含文字、代码、表格、图片；导入后可以检索、回答和打开来源。图片理解是首版核心能力。保持解析、切片、嵌入、索引、检索、回答和引用的职责分离。

已确定保留 Elasticsearch，使用 LangChain 压缩通用模型调用代码，保留少量可讲清楚的核心算法。网页要简洁完整，不使用 Gradio 作为最终界面。无关代码可直接删除，必要逻辑配中文注释。

不实现登录、企业安全平台、复杂异常恢复、高并发、消息队列、通用多格式平台或完整 RAGFlow。面试亮点集中在信息保留、父子切片、混合检索、证据窗口与来源验证，不追求功能清单长度。

## 面试讲解的三个边界

1. **信息完整不等于信息密度。** 前者是输入事实是否保留，后者是实际证据中的相关内容占比。用一个问题说明做法、代价和验证，不承诺“绝对保证”。
2. **分层有不同含义。** 接口/服务/RAG 模块/外部适配是工程职责；入库/问答是流程；文档/父块/子块是数据粒度。现有代码仍有直接依赖，不宣称严格解耦或微服务架构。
3. **只借鉴 RAGFlow 的部分机制。** 上游本身也有模块化与任务编排。我们选择适合 Markdown 的结构解析、图片描述和父块补充思路，不要求每个模块对齐上游，也不复制其企业基础设施。

## 技术基线

FastAPI + LangChain 模型组件 + markdown-it-py + ES + SQLite + 本地原文/图片 + 原生单页网页。内部使用 Document 和少量明确元数据，不建立复杂类型体系。

具体参数、字段、入口及接口以 [plan.md](D:/code/ragFlow-main/docs/plan/plan.md) 为准。当前源码已有父子切片、混合检索和窗口逻辑，问答路由仍未启用，图片理解与目标网页尚未实现。重构前参考统计为约 57 个 Python 文件、6602 行（含注释、空行），不计本地上游。

原实现父块和窗口上限均为 768 tokens，常发送完整父块。v1 选择 384-token 命中窗口作为起点，并保留完整父块对照验证；这是明确的设计选择，不是已经取得的性能结果。

## 权限仅作后续扩展

首版不实现登录、用户等级、分享和权限执行。后续参考飞书公开文档中的“密级策略 + 协作者授权”：本项目文档 1–4 级，1–2 级企业内公开，3–4 级由所有者/管理者授予阅读权限并受密级分享策略约束。

四级划分是本项目约定，不把“用户等级数字 ≥ 文档等级”声称为飞书既定实现。[飞书权限说明](https://www.feishu.cn/hc/zh-CN/articles/360049067494-%E7%94%B3%E8%AF%B7%E4%BA%91%E6%96%87%E6%A1%A3%E6%9D%83%E9%99%90?slug=true)。
