# RAG 评测：契约、实录与速查

更新日期：2026-09-28。本文是评测数据契约、真实运行记录与参数速查的唯一文档。项目总体优先级以 [`README.md`](README.md) 为准；算法概念见 [`算法层QA.md`](算法层QA.md)；面试口径见 [`docs/interview/评测与调参口径.md`](../interview/评测与调参口径.md)。本文内部阶段统一使用 `E0–E3`，与项目全局 P0/P1/P2 编号无关。

> **一句话结论（首次真实调参，2026-09-19）**：默认混合检索召回 88.2%、反被纯向量压着打；从融合分数机制提出假设并进行单变量调参后，锁定配置在 120 道 Test 上召回 97.5%、反超纯向量 5 个点；回答侧 evidence recall 93.1%、引用有效率 96.7%、P95 延迟 2.3 秒——历史总成本估算约两块钱，效果指标可由保存的 run 离线复算。

> **2026-09-28 实现变更**：混合融合已换为等权 RRF（k=60），`fused_score = Σ1/(60+rank) ÷ (2/61)`；固定缩放不改变排序，旧权重参数已删除。本文历史成绩均来自 Weighted Sum，不代表 RRF 已验证提升。旧阈值、规则重排加分和锁定配置需重新评测；历史 run 可离线复算，含旧权重的配置不能直接传入当前接口。

## 第一部分：数据与执行契约（E0–E3）

### 1.1 当前决策

主评测集使用 `CRUD-RAG-mini-v1`，不再继续扩建 T2Retrieval。首版固定为：

- 1,000 篇中文文本：全部正例文档 + 普通干扰项 + 相似主题困难干扰项。
- 150 条问答：`questanswer_1doc`、`questanswer_2docs`、`questanswer_3docs` 各 50 条。
- 30 条 Dev（每类 10 条）用于调参；120 条 Test（每类 40 条）只用于最终比较。
- 150 条问题使用不同的事件 ID，Dev/Test 间也不存在事件重叠。
- 固定上游 Git commit、`seed=42`、规范化算法版本和全部产物 SHA256。

选择这个规模的原因：它足以完成个人项目的固定同集 A/B、失败分析和面试讲解，又不会产生不必要的模型费用。它只能证明在这个受控子集上的相对效果，不能代表 8 万文档或企业级流量。

### 1.2 数据来源与边界

原始数据位于本地 `dataset/CRUD_RAG/`，整个目录必须被 Git 忽略。评测代码只读取数据，不安装或导入上游 CRUD-RAG 的旧版依赖。

构建时以 `data/crud_split/split_merged.json` 中问答样本自带的 `news1/news2/news3` 作为正例证据。上游 8 万文档没有可依赖的稳定 doc-id/qrels 映射，因此只作为干扰文档来源，不能通过模糊匹配猜测正例身份。

稳定标识：

```text
normalized_text = Unicode NFKC + CRLF/CR→LF + 行内空白折叠 + strip
doc_id          = "crud_" + sha256(normalized_text)[:24]
query_id        = "crud_q_" + sha256(task + event_id + question)[:24]
```

若两条正例规范化后相同，则共享同一个 `doc_id`；qrels 必须去重。普通/困难干扰项不得与任一正例完全相同或规范化后相同。

### 1.4 评测运行契约

指标口径以 `evaluation/score_run.py` 为准：Evidence Recall 计算进入证据的正例文档比例；Citation Validity 计算引用文档属于证据集合的比例；Citation Document Precision 计算引用文档属于 qrels 正例集合的比例。三者均为文档级指标，不能代替事实覆盖或逐条引用支持关系。

真实检索/问答链路只运行一次并录制 JSONL，确定性 scorer 可以反复离线计算。每条 run 至少保存：

- 数据集 ID、Git commit、配置指纹和模型名（不保存密钥）。
- `query_id`、检索候选的 `doc_id/rank/score/channel`。
- 实际进入 Prompt 的 evidence `doc_id`。
- 回答、引用 `doc_id`、状态和错误。
- 检索/生成/总延迟、输入/输出 token 和可得的成本。

E0 已实现的确定性指标：

- Retrieval：Hit@1/3/5/10、Recall@1/3/5/10、MRR@10、nDCG@10。
- Evidence：Evidence Recall、Evidence Precision；多文档问题必须按所需文档集合计算。
- Citation：Citation Validity 和 Citation Document Precision；E0 不伪装成 claim-level correctness。
- Performance：P50/P95 延迟、token/cost 汇总（字段不可得时明确记为 unavailable）。
- 分片：总分以及 1doc/2docs/3docs 三类分别报告。

E2 才引入 LLM Judge。首版固定抽取 Test 中 50 条（15/15/20）评 Faithfulness、Answer Correctness、Answer Relevancy 和 Context Precision/Recall；必须保存 rubric、模型版本、原始理由，并由人类抽查校准。

#### 1.4.1 Runner 与生产代码的边界

`evaluation/runner` 负责读取固定数据、选择实验配置、调用生产服务并录制结果；不得复制 `backend/` 的解析、分块、检索、窗口、生成或引用算法。需要改变真实产品行为的开关必须先进入生产配置：

| 生产接口 | 当前状态 | Runner 接入（历史 E1 已完成） | 已有验收证据 |
|---|---|---|---|
| 检索模式 | √ `RetrievalConfig.retrieval_mode = vector/keyword/hybrid` 已进入生产链路 | Runner 保存实际模式并调用同一生产入口 | 单测断言未选通道调用次数为 0，单通道分数使用有效权重 |
| Rerank 漏斗 | √ `rerank_top_n`、off/on、backend 和失败回退已实现 | Runner 保存实际漏斗并完成真实 A/B | 已校验 `top_k <= rerank_top_n <= candidate_top_k`；Trace 保存 backend/model/送排数/fallback |
| Evidence Window | √ 请求级 `QAConfig` 已支持 `child_only/window/full_parent` | Runner 在 Dev 传不同配置并原样录制 | 同一进程逐请求配置测试通过；Trace 保存最终生效值 |
| QA 可观测性 | √ 已返回请求级 `trace.config/timings_ms/usage` | Runner 原样写入 run schema，不从日志反推 | retrieval/window/generation/citation/total 和 usage 回归通过；不可得字段为 `unavailable` |

Runner 当前结构：

```text
evaluation/runner/
├── production_adapter.py  # 将生产 payload 映射为已冻结 run schema
├── index_dataset.py       # 调用 IngestionPipeline，写独立评测索引
├── run_retrieval.py       # 调用 HybridRouter，不调用 Chat
├── run_qa.py              # 调用 QAService 完整链路
└── sweep.py               # 只在 Dev 编排单变量参数扫描
```

评测索引必须使用独立名称，并生成 `index_manifest.json`，至少包含 dataset manifest SHA、Git commit、ES index、Embedding 模型、chunk profile/version/hash、成功/失败文档数和 Chunk 数。CRUD-RAG 的原始 `doc_id` 必须保留，否则无法与 qrels 对齐。

## 第二部分：首次真实调参实录（2026-09-19）

本部分保留 2026-09-19 的 `crud_rag_mini_v1` 历史 run、锁定配置和指标，按"问题 → 机制假设 → 尝试 → 结果"组织。这些结果不代表当前 v3 分块、GLM QA 默认模型或新增 Parent 重排已重新完成全链路评测。2026-09-23 校正指标名称和因果表述，没有改写历史分数。

### 2.1 问题：理论上最强的 hybrid，实测反而拉胯

四种检索模式、生产默认参数（`top_k=5, candidate_top_k=30, threshold=0.1, 权重 0.75/0.25, rerank off`），Dev 30 题基线：

| Dev（30 题） | Recall@10 | MRR@10 | nDCG@10 |
|---|---:|---:|---:|
| vector 纯向量 | **0.9556** | **0.9167** | **0.9126** |
| keyword 纯 BM25 | 0.9444 | 0.8778 | 0.8678 |
| hybrid 默认混合 | 0.8667 | 0.8861 | 0.8355 |
| hybrid_rerank 混合+规则重排 | 0.9222 | 0.8500 | 0.8600 |

教科书说混合检索取长补短，实测比单通道还差 8.9 个点。预期和实测相反——这就是要讲的问题。

### 2.2 定位：机制假设与实验观察

1. **比较单通道基线**：keyword 单独 recall 为 0.944，说明 BM25 在这个子集上并不弱；需要继续检查融合、父块聚合与最终截断，不能据此排除 BM25 的逐题错误。
2. **读代码提出假设**：Child 融合分为 `0.75×向量分 + 0.25×关键词分`，BM25 按本次最高分归一。在存在正分命中时，头名的关键词贡献为 0.25；这可能改变候选顺序，但不证明头名必然是错误文档。
3. **观察池深扫描**：候选池 10/30/50/100 对应 recall 0.944/0.867/0.822/0.889。10→50 下降，100 时回升，**不是单调关系**；本轮支持优先选择浅池，不能证明“越大越差”。
4. **限定归因**：池深变化还会改变同父块命中的 Child 集合及 mean 聚合分，阈值和最终返回名额也参与结果。尚未通过固定候选、替换归一化或逐题贡献消融隔离唯一原因，因此“归一化污染”保留为机制假设。

### 2.3 尝试：三个方向，一个失败但有用

先立规矩再动手（防"过拟合式调参"）：只用 30 道 Dev 调、一次只动一个旋钮共 20 组（拒绝 864 种全组合）、选择标准事前定死（recall@10 优先，同分看 mrr@10）、120 道 Test 锁住只在最后跑一次。

**方向一：调整候选池、阈值与返回名额（最终采纳）**

| 轴 | 各档位 recall@10 | 最优及理由 |
|---|---|---|
| candidate_top_k | 10→**0.9444**；30→0.8667；50→0.8222；100→0.8889 | 10：本轮 Dev 单轴最优；原因仍需候选贡献分析 |
| top_k | 3→0.7778；5→0.8667；10→**0.9444** | 10：名额直接抬召回 |
| similarity_threshold | 0→0.8556；0.05→0.8556；0.1→0.8667；0.2→**0.8944** | 0.2：低分噪声直接扔 |

**方向二：调融合权重 0.5~0.9 共 6 档（本轮没有额外收益）**

recall 在 0.84~0.87 之间，所扫档位没有超过默认权重的结果。这只能说明当前扫描范围内收益有限，不能证明权重不重要或归一化是唯一瓶颈。RRF 可减少对原始分数刻度的依赖，但本轮没有实现并比较它，不声称必然有效。

**方向三：规则重排（有效但按事前规则放弃）**

recall 0.8667→0.9222（+5.6pp），但 MRR 0.8861→0.8500（-3.6pp）。QA 场景只有前几名进提示词，头部顺序比池尾召回值钱；规则是事前定的（recall 增益 ≥1pp 且 MRR 不降才默认开），不是看着结果挑的。Test 上 hybrid_rerank 为 0.9569，锁定配置为 0.9750；两组不止一个参数不同，不能用该比较单独判断重排开关的因果效果。

### 2.4 结果：锁定配置 Test 一次验货，97.5%

锁定配置（通过生产 `build_retrieval_config` 校验）：

```json
{"candidate_top_k": 10, "top_k": 10, "similarity_threshold": 0.2, "vector_weight": 0.75, "rerank_enabled": false}
```

Dev 整体复验 recall@10 = 0.9722（组合配置优于各单轴结果，但没有证明各轴收益可独立相加）。Test 120 题只跑一次、不回头调：

| Test（120 题） | Recall@10 | MRR@10 | nDCG@10 |
|---|---:|---:|---:|
| vector | 0.9236 | **0.9040** | 0.8725 |
| keyword | 0.8819 | 0.8153 | 0.8026 |
| hybrid（默认参数） | 0.8819 | 0.8432 | 0.8203 |
| hybrid_rerank | 0.9569 | 0.8953 | 0.8911 |
| **locked（锁定 hybrid）** | **0.9750** | 0.8913 | 0.8895 |

锁定配置比默认 hybrid 的宏平均 Recall@10 高 9.31pp，反超纯向量 5.1pp。按历史 run 逐题去重文档并与 qrels 求交，命中的问题—文档对从 **207 增至 232，增加 25 对**；宏平均召回差不能直接乘 120 换算成文档数。MRR 略低于 vector（0.8913 vs 0.9040），具体原因需逐题分析，不能直接归咎于阈值。若未来改成 MRR 优先，应开启新一轮 Dev 选型并使用独立验收数据，不依据这批 Test 回调参数。

### 2.5 下半场：证据模式与回答质量（DeepSeek）

**Dev 扫描（5 配置 × 30 题，选型）**

历史 Dev 证据扫描中，五种配置的 evidence_recall 都是 0.8667。这表示进入 Prompt 的宏平均正例文档覆盖率相同，不代表证据文本或事实覆盖相同；也不应与上节组合检索配置的 0.9722 混为同一次运行。引用有效率存在差异：

| 证据配置（Dev） | citation_validity | P95 (ms) | input tokens/30 题 |
|---|---:|---:|---:|
| child_only | 0.7667 | 1927 | 15,269 |
| window 256 | 0.9000 | 2348 | 58,791 |
| window 384 | 0.8667 | 2297 | 64,982 |
| window 512 | 0.8667 | 2016 | 47,986 |
| **full_parent** | **0.9333** | 1905 | 42,393 |

锁定 **full_parent**：本轮 Dev 引用有效率最高、实测 P95 最低。未做隔离计时对照，不能把总延迟差全部归因于窗口拼接。

**Test 正式 run（锁定检索配置 × 3 种证据模式 × 120 题）**

120 题 × 3 变体全部 `ok`，零失败、零 no_evidence：

| Test（120 题） | evidence_recall | citation_validity | 引用文档精度 | P50 / P95 延迟 | input tokens/120 题 |
|---|---:|---:|---:|---:|---:|
| locked_child_only | 0.9306 | 0.8167 | 0.6647 | 1.06s / 1.81s | 56,013 |
| locked_window | 0.9306 | 0.9417 | 0.8579 | 1.24s / 2.41s | 205,231 |
| **locked_full_parent** | **0.9306** | **0.9667** | **0.8736** | 1.23s / 2.29s | 159,296 |

三个结论：

1. **evidence_recall 0.9306 三者相同**——本轮三个模式的宏平均正例文档覆盖率相同；一般情况下 context_top_k、证据模式与总预算淘汰也会改变这个指标，不能说它只由检索决定；
2. **full_parent 双赢**：引用有效率最高（0.9667），且本轮输入 token 比 window-384 少 22%（不代表任意语料都更省）——Dev 选型在 Test 上成立；
3. **child_only 的取舍**：相对 full_parent，输入 token 约为其 35%，但引用有效率低 15 个百分点；本轮依据引用指标选择 full_parent，没有据此声称语义回答质量已经过 Judge 验证。

最终全链路（锁定检索 + full_parent）：**召回 97.5%，evidence recall 93.1%，引用有效率 96.7%，P95 2.3s**。

**历史成本估算**：全量索引 + 全部评测 ≈ ¥2（索引走 GLM embedding-3；生成走 DeepSeek，Dev 实测 150 次调用 22.9 万输入 + 1.8 万输出 token ≈ ¥0.6）。

用途：忘了某个参数/指标是什么意思、默认值多少、锁定了哪个，翻这一部分。试错过程见第二部分，执行契约见第一部分。

### 3.1 检索漏斗参数（RetrievalConfig）

以下默认值来自当前 `config/defaults.yaml`，锁定值来自 2026-09-19 历史实验；锁定配置未自动替换生产默认值。

共同入口：问题 → 每个启用通道召回 candidate_top_k 个 Child → 融合去重。融合池最多可有两倍 candidate_top_k 个 Child。

- 不重排：Child 融合分过滤 → 按 Parent 做 mean/max 聚合 → 取 top_k。
- Child 重排：取前 rerank_top_n 个 Child → rule/CE 重排 → 按重排后分数过滤 → Parent mean/max 聚合 → 取 top_k。
- Parent 重排：取同样的 Child 池 → 恢复并去重 Parent → Parent CE 重排 → 按 Parent CE 分过滤 → 取 top_k。
- 重排失败：回退完整融合池，再按 Child 融合分过滤和所选 mean/max 聚合；父块缺失时保留主命中 Child 并记录降级。

正常路径的 top_k 是聚合后的父块数；QA 再用 context_top_k 选择进入证据构造的结果。

| 参数 | 默认值 | 锁定值 | 含义 | 调大/调小的效果 |
|---|---|---|---|---|
| `retrieval_mode` | hybrid | hybrid | 通道门控：vector 只走向量 / keyword 只走 BM25 / hybrid 两路都走。严格消融靠它，不是把权重设 0 | — |
| `candidate_top_k` | 30 | **10** | 每条通道捞多少候选（海选池大小） | 改变召回覆盖和命中 Child 的父块聚合组成，收益不保证单调 |
| `top_k` | 5 | **10** | 聚合后最终返回的父块数；缺失父块时可回落 Child | 调大→召回涨、精度可能摊薄 |
| `similarity_threshold` | 0.1 | **0.2** | 作用于实际重排粒度上的最终分数；未重排/失败回退时作用于 Child 融合分 | 调大→噪声少但可能误杀低分正例 |
| 融合策略（固定实现） | 等权 RRF，k=60 | 旧 Weighted Sum：0.75 / 0.25 | RRF 按名次计分并除以理论上限 2/61；旧权重参数已删除 | RRF 效果尚未评测；历史 6 档权重扫描只适用于旧实现 |
| `rerank_enabled` | false | false（决策关闭） | 是否做精细二次排序 | recall +5.6pp 但 MRR -3.6pp，QA 重头部 → 按事前规则放弃 |
| `rerank_backend` | rule | — | rule（免费规则）/ cross-encoder（模型，中文需显式配模型） | — |
| `rerank_top_n` | None（使用 candidate_top_k） | — | 选取的 Child 数；Parent 模式先按该数量取 Child，再按 Parent 去重送排；显式设置时要求 top_k ≤ rerank_top_n ≤ candidate_top_k | — |
| `rerank_level` | child | 历史为 Child 路径 | child / parent；parent 重排仅支持 cross-encoder | 改变模型评分的文本粒度，不扩大 Child 召回池 |
| `child_score_aggregation` | mean | 历史为 mean | mean / max；用于 Child 路径、关闭重排与失败回退，成功 Parent CE 不使用其分数 | max 可避免弱命中稀释强命中，仍需同集评测 |
| `filters` | None | — | 元数据过滤（如按 doc_id） | — |

### 3.2 QA 证据参数（QAConfig，请求级）

| 参数 | 默认值 | 锁定值 | 含义 |
|---|---|---|---|
| `evidence_mode` | window | **full_parent** | 喂给回答模型的证据切法：child_only 只给命中小碎块 / window 以命中点为中心扩窗口 / full_parent 整块父块 |
| `evidence_window_tokens` | 384 | — | window 模式的窗口大小（本次扫 256/384/512，full_parent 胜出） |

| 参数 | 值 | 含义 |

| parent_target / max tokens | 512 / 768 | 普通正文父块目标/硬上限 token |

### 3.5 指标含义速查（见到指标 → 它回答什么问题）

| 指标 | 回答什么问题 | 及格直觉 |
|---|---|---|
| Hit@K | 前 K 里至少命中一个正例吗 | 看下限 |
| Recall@K | 该找到的文档，找到几成 | 检索侧主指标，调参第一标准 |
| MRR@10 | 第一个正确结果排多靠前（第 1 名=1，第 2 名=0.5…） | QA 场景比 recall 更值钱：只有头部进提示词 |
| nDCG@10 | 整体排序质量（多个正例的顺序合不合理） | 综合参考 |
| Evidence Recall | 所需正例文档有多少进入 Prompt 证据集合 | 文档级覆盖，不测片段是否包含所需事实；同时受检索、选取和预算影响 |
| Citation Validity | 引用文档属于给出的证据集合吗 | 引用来源有效性；历史 Dev 的 child_only 0.77 vs full_parent 0.93，不测逐句支持关系 |
| Citation Document Precision | 引用的文档是正例吗 | 引用准不准 |
| P50/P95 延迟 | 一半/95% 请求多快 | P95 看长尾 |
| usage（input/output tokens） | 真实消耗，算成本用 | 不可得记 unavailable，不补零 |
| source_span accuracy | 来源坐标精度：exact 可逐字高亮 / line_only 只到行 / unavailable 不画假高亮 | 诚实分级，不冒充 exact |

真实成绩单见第二部分 §2.4/§2.5 的表格，此处不再重复。
