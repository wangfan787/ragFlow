# RAG 评测实施计划

更新日期：2026-09-17。

本文是评测数据、运行文件和评分口径的执行契约。项目总体优先级仍以 [`README.md`](README.md) 为准；算法概念见 [`算法层QA.md`](算法层QA.md)。

## 1. 当前决策

主评测集使用 `CRUD-RAG-mini-v1`，不再继续扩建 T2Retrieval。首版固定为：

- 1,000 篇中文文本：全部正例文档 + 普通干扰项 + 相似主题困难干扰项。
- 150 条问答：`questanswer_1doc`、`questanswer_2docs`、`questanswer_3docs` 各 50 条。
- 30 条 Dev（每类 10 条）用于调参；120 条 Test（每类 40 条）只用于最终比较。
- 150 条问题使用不同的事件 ID，Dev/Test 间也不存在事件重叠。
- 固定上游 Git commit、`seed=42`、规范化算法版本和全部产物 SHA256。

选择这个规模的原因：它足以完成个人项目的固定同集 A/B、失败分析和面试讲解，又不会产生不必要的模型费用。它只能证明在这个受控子集上的相对效果，不能代表 8 万文档或企业级流量。

## 2. 数据来源与边界

原始数据位于本地 `dataset/CRUD_RAG/`，整个目录必须被 Git 忽略。评测代码只读取数据，不安装或导入上游 CRUD-RAG 的旧版依赖。

构建时以 `data/crud_split/split_merged.json` 中问答样本自带的 `news1/news2/news3` 作为正例证据。上游 8 万文档没有可依赖的稳定 doc-id/qrels 映射，因此只作为干扰文档来源，不能通过模糊匹配猜测正例身份。

稳定标识：

```text
normalized_text = Unicode NFKC + CRLF/CR→LF + 行内空白折叠 + strip
doc_id          = "crud_" + sha256(normalized_text)[:24]
query_id        = "crud_q_" + sha256(task + event_id + question)[:24]
```

若两条正例规范化后相同，则共享同一个 `doc_id`；qrels 必须去重。普通/困难干扰项不得与任一正例完全相同或规范化后相同。

## 3. 冻结产物

生成目录与 `backend/` 同级：

```text
evaluation/
├── README.md
├── build_dataset.py
├── validate_dataset.py
├── score_run.py
├── report.py
├── schemas.py
├── datasets/crud_rag_mini_v1/  # 本地生成，不提交 Git
├── runs/                         # 真实链路录制，不提交 Git
├── scores/                       # 离线评分结果，不提交 Git
├── reports/generated/            # 生成报告，不提交 Git
└── tests/
```

数据集目录包含：

```text
README.md
manifest.json
corpus.jsonl
queries.dev.jsonl
queries.test.jsonl
qrels.jsonl
references.jsonl
```

每条 query 保存 `query_id`、`task`、`event_id`、`question`、`answer` 和 `split`；每条 qrel 保存 `query_id`、`doc_id`、`relevance=1`。`references.jsonl` 保存问题到所需正例集合的映射，不能只保留答案文本。

## 4. 评测运行契约

真实检索/问答链路只运行一次并录制 JSONL，确定性 scorer 可以反复离线计算。每条 run 至少保存：

- 数据集 ID、Git commit、配置指纹和模型名（不保存密钥）。
- `query_id`、检索候选的 `doc_id/rank/score/channel`。
- 实际进入 Prompt 的 evidence `doc_id`。
- 回答、引用 `doc_id`、状态和错误。
- 检索/生成/总延迟、输入/输出 token 和可得的成本。

P0 的确定性指标：

- Retrieval：Hit@1/3/5/10、Recall@1/3/5/10、MRR@10、nDCG@10。
- Evidence：Evidence Recall、Evidence Precision；多文档问题必须按所需文档集合计算。
- Citation：Citation Validity 和 Citation Document Precision；P0 不伪装成 claim-level correctness。
- Performance：P50/P95 延迟、token/cost 汇总（字段不可得时明确记为 unavailable）。
- 分片：总分以及 1doc/2docs/3docs 三类分别报告。

P1 才引入 LLM Judge。首版固定抽取 Test 中 50 条（15/15/20）评 Faithfulness、Answer Correctness、Answer Relevancy 和 Context Precision/Recall；必须保存 rubric、模型版本、原始理由，并人工抽查。

## 5. P0 任务清单

### P0-A：冻结数据集

- [ ] 实现确定性构建 CLI，固定 50/50/50、30/120、事件隔离和 `seed=42`。
- [ ] 确保所有 qrels 正例都存在于 1,000 文档语料，且文档 ID 唯一。
- [ ] 加入普通与相似主题干扰项；排除正例的规范化重复。
- [ ] 写入 source commit、算法版本、参数、文件行数/字节数/SHA256。
- [ ] 生成本地 `crud_rag_mini_v1`，并用独立 validator 验收。

### P0-B：确定性评分闭环

- [ ] 定义 run JSONL schema，拒绝未知 query/doc、重复排名和缺失必填字段。
- [ ] 实现 Retrieval、Evidence、Citation、Performance scorer。
- [ ] 按 overall/1doc/2docs/3docs 输出机器可读 JSON。
- [ ] 从同一 score JSON 生成 Markdown 报告，避免手填指标。

### P0-C：回归保护与可运行说明

- [ ] 单测覆盖确定性、事件隔离、正例完备、hash 校验和指标手算样例。
- [ ] 在 Conda `agent` 环境运行测试并记录真实结果。
- [ ] 文档给出 build→validate→score→report 命令，不要求安装 CRUD-RAG 上游依赖。

P0 完成定义：任意人拿到同一上游 commit，运行构建命令得到相同的 1,000/150 数据、相同 hash；一个符合 schema 的 run 能离线得到确定性指标和报告。P0 不要求付费调用模型，也不虚构尚未运行的真实检索 baseline。

## 6. P1 与 P2

P1：把生产检索/QA 链路接到 runner；完成 Vector、Hybrid Weighted Sum、Rerank off/on 的同集 A/B；扫描 TopK、阈值和 evidence window；对固定 50 条做有人工校准的 LLM Judge。

P2：只有失败数据证明必要时，才扩大语料/问题规模、实现 Weighted RRF、增加不可回答/安全/图片/权限业务集，或引入第三方评测框架。当前不建设 Agent 评测。

## 7. 面试口径

> 我从 CRUD-RAG 固定抽取 1,000 篇文档和 150 条分层问答，1/2/3 文档问题各 50 条。所有正例强制入库，再加入普通和困难干扰项；Dev/Test 按事件 ID 隔离，并固定上游 commit、随机种子、算法版本和文件哈希。全量 150 条计算确定性检索、证据、引用和性能指标，语义 Judge 只在固定 Test 子集上运行并人工校准。这个 Mini Benchmark 用于低成本、可复现的方案比较，不宣称等价于全量或线上效果。
