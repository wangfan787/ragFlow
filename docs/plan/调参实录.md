# 首次真实调参实录（试错记录）

更新日期：2026-09-19。本文记录 `crud_rag_mini_v1` 上第一次真实评测调参全过程，按"问题 → 定位 → 尝试 → 结果"组织。

**一句话结论：默认混合检索召回 88.2%、反被纯向量压着打；定位到融合层分数归一化污染后单变量调参，锁定配置在 120 道 Test 上召回 97.5%、反超纯向量 5 个点；回答侧 evidence recall 93.1%、引用正确率 96.7%、P95 延迟 2.3 秒——全程成本约两块钱，每个数字都能离线复算。**

## 1. 问题：理论上最强的 hybrid，实测反而拉胯

四种检索模式、生产默认参数（`top_k=5, candidate_top_k=30, threshold=0.1, 权重 0.75/0.25, rerank off`），Dev 30 题基线：

| Dev（30 题） | Recall@10 | MRR@10 | nDCG@10 |
|---|---:|---:|---:|
| vector 纯向量 | **0.9556** | **0.9167** | **0.9126** |
| keyword 纯 BM25 | 0.9444 | 0.8778 | 0.8678 |
| hybrid 默认混合 | 0.8667 | 0.8861 | 0.8355 |
| hybrid_rerank 混合+规则重排 | 0.9222 | 0.8500 | 0.8600 |

教科书说混合检索取长补短，实测比单通道还差 8.9 个点。预期和实测相反——这就是要讲的问题。

## 2. 定位：四步推理链，实验反证闭环

1. **排除通道本身**：keyword 单独跑 recall 0.944，不弱 → 坏的不是 BM25，是融合这一步。
2. **看数据特性**：新闻问答，问法和正文用词大量重叠，两条通道命中高度重合 → 只解释"没赚"，不解释"倒亏"，继续往下挖。
3. **读融合代码找到机制**：融合分 = `0.75×向量 + 0.25×关键词`，关键词分按"本题最高分=1"归一 → 每道题必然有一个文档白得 0.25 加分；新闻高频词（记者/大会/年份）让 BM25 头名经常是错文档 → 错文档 0.30(向量)+0.25(白送) > 对文档 0.55(只在向量命中) → **正例被挤出前十，倒亏就是这么来的**。
4. **实验反证**：候选池 10/30/50/100 → recall 0.944 / 0.867 / 0.822 / 0.889，池子越大、弱关键词命中越多、污染越重——走势和推断一致，定位闭环。

## 3. 尝试：三个方向，一个失败但有用

先立规矩再动手（防"过拟合式调参"）：只用 30 道 Dev 调、一次只动一个旋钮共 20 组（拒绝 864 种全组合）、选择标准事前定死（recall@10 优先，同分看 mrr@10）、120 道 Test 锁住只在最后跑一次。

**方向一：沿根因治理（有效，最终采纳）**

| 轴 | 各档位 recall@10 | 最优及理由 |
|---|---|---|
| candidate_top_k | 10→**0.9444**；30→0.8667；50→0.8222；100→0.8889 | 10：少捞弱关键词命中 |
| top_k | 3→0.7778；5→0.8667；10→**0.9444** | 10：名额直接抬召回 |
| similarity_threshold | 0→0.8556；0.05→0.8556；0.1→0.8667；0.2→**0.8944** | 0.2：低分噪声直接扔 |

**方向二：调融合权重 0.5~0.9 共 6 档（失败，但反向确认定位正确）**

recall 全卡在 0.84~0.87 的平台上，动权重没用——说明瓶颈不在权重比例，在归一化机制，定位对了。顺势的技术判断：RRF（按名次融合、免疫分数刻度问题）能治这个病，但便宜的参数治理已经把收益拿满，按"失败证据触发"原则不提前上复杂方案。

**方向三：规则重排（有效但按事前规则放弃）**

recall 0.8667→0.9222（+5.6pp），但 MRR 0.8861→0.8500（-3.6pp）。QA 场景只有前几名进提示词，头部顺序比池尾召回值钱；规则是事前定的（recall 增益 ≥1pp 且 MRR 不降才默认开），不是看着结果挑的。Test 上 hybrid_rerank 0.9569 也确实没超过锁定配置 0.9750，事后看决策正确。

## 4. 结果：锁定配置 Test 一次验货，97.5%

锁定配置（通过生产 `build_retrieval_config` 校验）：

```json
{"candidate_top_k": 10, "top_k": 10, "similarity_threshold": 0.2, "vector_weight": 0.75, "rerank_enabled": false}
```

Dev 整体复验 recall@10 = 0.9722（各轴收益确实叠加，单轴最高只有 0.9444）。Test 120 题只跑一次、不回头调：

| Test（120 题） | Recall@10 | MRR@10 | nDCG@10 |
|---|---:|---:|---:|
| vector | 0.9236 | **0.9040** | 0.8725 |
| keyword | 0.8819 | 0.8153 | 0.8026 |
| hybrid（默认参数） | 0.8819 | 0.8432 | 0.8203 |
| hybrid_rerank | 0.9569 | 0.8953 | 0.8911 |
| **locked（锁定 hybrid）** | **0.9750** | 0.8913 | 0.8895 |

调参后的 hybrid 比默认多找回约 11 篇/120 题，反超纯向量 5.1pp。MRR 略低于 vector（0.8913 vs 0.9040）是阈值挡掉个别低分高排名候选的代价；业务若更在意第一名正确率，把选择标准换成 MRR 优先重扫一轮即可——选择标准是旋钮，不是教条。

## 5. 下半场：证据模式与回答质量（DeepSeek）

### 5.1 Dev 扫描（5 配置 × 30 题，选型）

检索调到天花板后扫证据构造。evidence_recall 五种配置全部 0.8667——被检索上限压住，再次验证"Recall 决定天花板"；差异在引用质量：

| 证据配置（Dev） | citation_validity | P95 (ms) | input tokens/30 题 |
|---|---:|---:|---:|
| child_only | 0.7667 | 1927 | 15,269 |
| window 256 | 0.9000 | 2348 | 58,791 |
| window 384 | 0.8667 | 2297 | 64,982 |
| window 512 | 0.8667 | 2016 | 47,986 |
| **full_parent** | **0.9333** | 1905 | 42,393 |

锁定 **full_parent**：引用正确率最高、延迟最低（父块直接命中不用拼窗口）。

### 5.2 Test 正式 run（锁定检索配置 × 3 种证据模式 × 120 题）

120 题 × 3 变体全部 `ok`，零失败、零 no_evidence：

| Test（120 题） | evidence_recall | citation_validity | 引用文档精度 | P50 / P95 延迟 | input tokens/120 题 |
|---|---:|---:|---:|---:|---:|
| locked_child_only | 0.9306 | 0.8167 | 0.6647 | 1.06s / 1.81s | 56,013 |
| locked_window | 0.9306 | 0.9417 | 0.8579 | 1.24s / 2.41s | 205,231 |
| **locked_full_parent** | **0.9306** | **0.9667** | **0.8736** | 1.23s / 2.29s | 159,296 |

三个结论：

1. **evidence_recall 0.9306 三者相同**——证据召回由检索决定，证据模式只决定"给模型看的文本够不够答题"，这一层再次和 §2 的"Recall 决定天花板"互相印证；
2. **full_parent 双赢**：引用正确率最高（0.9667），且输入 token 比 window-384 少 22%（父块直接给，比拼窗口更省）——Dev 选型在 Test 上成立；
3. **child_only 的 token 省得不值**：输入只有 1/3，但引用正确率掉 15 个点；每题省约 ¥0.004，质量损失不可接受。

最终全链路（锁定检索 + full_parent）：**召回 97.5%，evidence recall 93.1%，引用正确率 96.7%，P95 2.3s**。

## 6. 面试口径

### 一分钟版本（先背这个）

> 第一次给 RAG 跑真实评测就碰见一个反直觉的问题：理论上应该最强的混合检索，召回率反而比纯向量低了 9 个点。我先做排除法：关键词单通道召回 94%，不弱，说明坏的不是 BM25，是融合这一步；再读融合代码找到机制——BM25 分数按"本题最高分归一为 1"，等于每道题必然有一个文档白得 0.25 的加分，而新闻语料高频词多，拿这个加分的经常是错文档，它把只在向量通道命中的正例挤出了前十。我用一个实验反向验证：候选池从 10 扩到 50，召回从 94% 一路掉到 82%，和"池子越大污染越多"的推断完全一致。解决上我试了三个方向：沿根因缩小候选池、提高阈值——有效；调融合权重，扫了 6 档没变化——没用，但反向确认瓶颈不在权重；开规则重排——召回加 5.6 个点但 MRR 掉了，QA 场景只有前几名进提示词，按事前定好的规则放弃。最终锁定配置在 120 道 Test 题上召回从 88.2% 提到 97.5%，反超纯向量 5 个点；回答侧又做了证据模式 A/B，整块父块做证据拿到引用正确率 96.7%、P95 延迟 2.3 秒，比拼窗口质量更高还更省 token。整个评测调参全程只花了两块钱，每题的真实延迟和 token 都录在 run 文件里，随时可以复算。

### 按追问展开

**Q：碰见了什么问题？**
默认参数下 hybrid recall@10 只有 0.867，纯向量 0.956（Dev 30 题）。教科书说混合取长补短，实测比单通道还差 9 个点——问题本身就是"预期和实测相反"。

**Q：怎么定位的？**（讲推理链，不要直接跳答案）
1. 排除通道本身：keyword 单独 0.944，不弱 → 不是 BM25 的问题；
2. 看数据特性：问法和正文用词大量重叠、两通道命中高度重合 → 只解释"没赚"；
3. 读融合代码找机制：BM25 按本题最高分归一 → 每题必有一个文档白得 0.25 加分 → 高频词让拿分的多是错文档 → 错文档压过只在向量命中的正例，解释"倒亏"；
4. 实验反证：池子 10/30/50/100 → 0.944/0.867/0.822/0.889，单调走势与推断一致，定位闭环。

**Q：尝试了什么方法？**（失败的也要讲）
1. 沿根因治理：池子 30→10、阈值 0.1→0.2、名额 5→10 → 有效，Test 97.5%；
2. 调融合权重 6 档 → 平台、没用 → 反向确认瓶颈在归一化机制不在权重；顺势讲 RRF 判断：能治但先不上，便宜的治理已拿满收益；
3. 规则重排 → recall +5.6pp / MRR -3.6pp → 按**事前**规则放弃，QA 头部顺序更值钱。

**Q：怎么保证不是过拟合调出来的？**
三道闸：只用 30 道 Dev 调、一次一个旋钮；选择标准（recall 优先）事前定死，不是看着结果挑；120 道 Test 锁到最后只跑一次。小分差（1~2 题波动 = 3~6pp）不解读，只解读单调走势和平台这类稳健信号——权重轴的"平台"就是这么读出来的。

**Q：结果怎么验证的？**
锁定配置先在 Dev 整体复验（0.9722），Test 一次验货 0.9750 vs 默认 hybrid 0.8819 vs 纯向量 0.9236。回答侧在 Test 上 120 题 × 3 种证据模式全量运行、零失败：evidence recall 93.1%、引用正确率 96.7%（full_parent）、P95 2.3s。每题真实延迟/token 录在 run JSONL，离线 scorer 可反复复算，全程成本约 ¥2。

**Q：回答质量怎么评的？没用 LLM Judge 靠谱吗？**
先用确定性指标：evidence recall（该进的证据文档进了提示词没有）、citation validity（引用的文档是不是真来自证据）、引用文档精度（引用是否指向正例）。这些不需要 Judge、可复算、不会漂移。语义层面的 Faithfulness/Correctness 需要人工校准过的 Judge 才可信，我把它排在下一阶段——没校准的 Judge 分数不如不报。

**Q：为什么不直接上 RRF？**
RRF 治的确实是分数刻度问题，是真解法；但参数治理先验证了主因是池子和阈值，收益已拿满，不提前上复杂方案。

**Q：这组参数能直接用到别的场景吗？**
参数不迁移，方法论迁移：基线 → 排除法 → 机制假设 → 实验反证 → 单变量扫描 → 锁定验货。换语料/换嵌入模型重跑一遍这套流程就行，我的 Runner 是现成的。
